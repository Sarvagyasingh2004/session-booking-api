# Session Booking API

REST API where teachers publish available sessions, users book them, and completed sessions show up in the user's history.

**Stack:** Node.js, TypeScript, Express.js, MongoDB, Mongoose (plus Zod for request validation).

## Setup

### Prerequisites
- Node.js 18 or newer
- A running MongoDB instance (local, Docker, or MongoDB Atlas)

Quick local MongoDB with Docker:

```bash
docker run -d --name mongo -p 27017:27017 mongo:7
```

### Install and run

```bash
npm install
cp .env.example .env      # then edit values if needed
npm run dev               # development, auto-restarts on changes
```

Production build:

```bash
npm run build
npm start
```

The server starts on `http://localhost:3000` by default. Check it with `GET /health`.

### Environment variables

| Variable      | Description                       | Default / example                              |
| ------------- | --------------------------------- | ---------------------------------------------- |
| `PORT`        | Port the server listens on        | `3000`                                         |
| `MONGODB_URI` | MongoDB connection string         | `mongodb://127.0.0.1:27017/session-booking`    |
| `NODE_ENV`    | `development`, `production`, `test` | `development`                                |

The app validates these at startup and exits with a clear message if something is missing.

## Testing with Postman

1. Import `postman/session-booking-api.postman_collection.json`.
2. Make sure the `baseUrl` collection variable matches your server (default `http://localhost:3000`).
3. Run the folder **Happy path** in order (or use the Collection Runner). Test scripts save `teacherId`, `userId` and `sessionId` automatically, and the session times are generated by a pre-request script, so nothing needs to be edited by hand.
4. Then run **Error cases** to see the validation and business-rule failures (400 / 404 / 409).

## API reference

All responses use the shape `{ "success": true, ... }` or `{ "success": false, "message": "...", "errors": [...] }`.

| # | Method & path                              | Description                               | Success |
| - | ------------------------------------------ | ----------------------------------------- | ------- |
| 1 | `POST /users`                              | Create a user (email unique)              | 201     |
| 2 | `POST /sessions`                           | Create an AVAILABLE session for a teacher | 201     |
| 3 | `GET /sessions/available?dateTimestamp=`   | AVAILABLE sessions on a date (aggregation)| 200     |
| 4 | `POST /sessions/:id/book`                  | Book a session                            | 200     |
| 5 | `PATCH /sessions/:id/complete`             | Mark a BOOKED session COMPLETED           | 200     |
| 6 | `GET /users/:id/sessions`                  | Upcoming and completed sessions (aggregation) | 200 |
| - | `POST /teachers`                           | Helper: create a teacher (see note below) | 201     |

> **Note on `POST /teachers`:** the assignment defines a Teacher schema but no endpoint to create one, and sessions need an existing teacher. This small extra endpoint makes the API testable end to end.

### 1. Create user
`POST /users`
```json
{ "fullName": "Rahul Verma", "email": "rahul@example.com", "phone": "+919876543210" }
```
Returns `409` if the email already exists.

### 2. Create session
`POST /sessions`
```json
{ "teacherId": "<teacher id>", "startTime": "2026-11-20T10:00:00Z", "endTime": "2026-11-20T11:00:00Z" }
```
- `startTime` / `endTime` must be ISO 8601 strings.
- `404` if the teacher does not exist, `400` if `endTime` is not after `startTime`.
- Status defaults to `AVAILABLE`.

### 3. Available sessions
`GET /sessions/available?dateTimestamp=1795168800000`

Returns all `AVAILABLE` sessions whose `startTime` falls on that date, sorted by start time, each with teacher details.
- `dateTimestamp` is a Unix timestamp in **milliseconds or seconds** (detected automatically).
- The date is interpreted as a **UTC calendar day**.
- Pipeline: `$match` (status + day range) → `$sort` → `$lookup` (teacher) → `$unwind` → `$project`.

### 4. Book session
`POST /sessions/:id/book` with body `{ "userId": "<user id>" }`
- `404` if the user or session does not exist.
- `409` if the session is not `AVAILABLE` (for example, already booked).
- Sets `status = BOOKED` and `userId`.

### 5. Complete session
`PATCH /sessions/:id/complete`
- `404` if the session does not exist.
- `409` unless the session is `BOOKED`.
- Sets `status = COMPLETED` and `completedAt` to the current time.

### 6. User sessions
`GET /users/:id/sessions`
```json
{
  "success": true,
  "data": {
    "userId": "...",
    "upcomingSessions":  [ { "_id": "...", "status": "BOOKED", "teacher": { "fullName": "..." } } ],
    "completedSessions": [ { "_id": "...", "status": "COMPLETED", "completedAt": "..." } ]
  }
}
```
- **Upcoming** = the user's `BOOKED` sessions, soonest first.
- **Completed** = the user's `COMPLETED` sessions, most recently completed first.
- Pipeline: `$match` (user + status) → `$lookup` (teacher) → `$unwind` → `$project` → `$facet` (two sorted lists in a single query).
- `404` if the user does not exist.

## Design notes

- **No double booking.** Booking and completing use a single atomic `findOneAndUpdate` that includes the expected status in the filter. If two users try to book the same session at the same moment, only one update matches; the other gets `409`.
- **Status codes:** `400` invalid input, `404` not found, `409` rule/state conflict (duplicate email, wrong session status), `500` unexpected errors (details hidden in production).
- **Centralized error handling:** controllers just throw. One middleware (`src/middlewares/errorHandler.ts`) converts `AppError`, Zod validation errors, Mongoose validation/cast errors, duplicate-key errors and malformed JSON into consistent responses.
- **Async/await only:** an `asyncHandler` wrapper forwards rejected promises from async controllers to the error middleware.
- **Indexes:** unique index on `User.email`; `Session` indexes on `{status, startTime}` and `{userId, status, startTime}` to back the two aggregation queries.
- **Not enforced (not in the requirements):** sessions in the past are allowed, and overlapping sessions for the same teacher are allowed.
